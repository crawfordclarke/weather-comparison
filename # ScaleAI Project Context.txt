# ScaleAI Project Context

## What I'm Building
An anime/manga fight simulator. Users pick two characters from any series, the app simulates a turn-by-turn fight grounded in actual lore. A fight engine handles mechanics (stats, damage, abilities), while the Gemini API narrates each turn using real character knowledge retrieved from a scraped wiki database (RAG). Community votes on whether the outcome was lore-accurate.

## Stack
- **Frontend:** React + TypeScript + Tailwind CSS
- **Backend:** FastAPI (Python)
- **AI Narration:** Google Gemini API (`gemini-2.5-flash`)
- **Vector DB / RAG:** pgvector (PostgreSQL extension)
- **Database:** Single PostgreSQL instance, running in Docker (`pgvector/pgvector:pg17`) — see "Database Architecture" below
- **Scraping:** BeautifulSoup + Fandom MediaWiki API
- **Auth:** Supabase Auth (planned, Slice 6)
- **Realtime:** WebSockets (planned, Slice 6)
- **Deploy:** Railway + Vercel (planned, Slice 7)
- **Package Manager:** uv
- **Dev Environment:** Windows, VS Code, PowerShell, pgAdmin 4 for DB inspection

## Database Architecture (IMPORTANT — recently changed)
Originally ran two separate Postgres instances (local Postgres on 5432 for `wiki_data`, Docker pgvector container on 5433 for `rag_text`), which meant no real foreign key could exist between them (cross-server FK is not possible in Postgres).

**This has been consolidated.** Both tables now live in the same database (`scaleai`) inside the **same Docker container** (`pgvector/pgvector:pg17`, container ID `bafcaa49d757`, named volume confirmed durable — `Type: volume` mounted at `/var/lib/postgresql/data`, not anonymous/ephemeral). `wiki_data` was migrated in via `pg_dump`/`pg_restore` and the old local Postgres instance is no longer used by the app. A real foreign key now exists between `rag_text.character_name` and `wiki_data.character_name`.

No `docker-compose.yml` yet — container was started via a raw `docker run` command. Connecting via pgAdmin 4 under connection name `scaleVector`.

### Slice 4 🔄 — RAG Pipeline (In Progress)
- Database consolidation complete (see Database Architecture above)
- `vector` extension confirmed enabled in the `scaleai` database (had to re-run `CREATE EXTENSION IF NOT EXISTS vector;` after migration, since extension state didn't carry over automatically)
- **`rag_text` table created and confirmed (via `information_schema.columns` and `pg_constraint` queries, since `\d` meta-commands don't work in GUI query editors):**
```sql
CREATE TABLE rag_text (
    id INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    character_name TEXT NOT NULL REFERENCES wiki_data(character_name),
    chunk_index INT NOT NULL,
    raw_text_chunk TEXT NOT NULL,
    embedding VECTOR(768)
);
```
- FK confirmed via `pg_get_constraintdef`: `FOREIGN KEY (character_name) REFERENCES wiki_data(character_name)`
- Embedding dimension set to 768 — assumed to match Gemini's `text-embedding-004` (fixed 768-dim) — **not yet 100% confirmed which embedding model/call will actually be used; if `gemini-embedding-001` is used instead, dimension is configurable (768/1536/3072 via `output_dimensionality`) so this needs to be locked in before generating real embeddings**
- **Immediate next step:** decide chunking strategy. Need to check:

  2. Whether section structure (headers) survived scraping, or if it's an undifferentiated text blob — determines whether structure-aware chunking is even possible vs. falling back to fixed-size/sentence-aware chunking
- **Remaining steps after chunking decided:**
  1. Write chunking logic, populate `chunk_index`
  2. Generate embeddings using Gemini Embeddings API (model TBD — see above)
  3. Store chunks + embeddings in `rag_text`
  4. Add an HNSW index on `embedding` once data exists: `CREATE INDEX ON rag_text USING hnsw (embedding vector_cosine_ops);`

## Key Decisions & Learnings
- Direct Fandom HTML scraping blocked by Cloudflare (403) — use MediaWiki API instead
- `gemini-2.0-flash` hit quota issues — `gemini-2.5-flash` works
- Dumping raw `turn_data` dict into narrator prompt works better than structured f-strings
- `load_dotenv()` must be called before `os.getenv()` at module level
- Run scripts from project root (`C:\dev\ScaleAI\`) with `python -m Backend.app.services.script`
- pgvector requires C++ build tools on Windows — Docker image sidesteps this entirely; ended up consolidating *all* Postgres into the Docker container rather than fighting the build tools route
- Cross-server foreign keys are not possible in Postgres — this was the actual reason for consolidating both databases into one instance/container, not just convenience
- GUI tools (pgAdmin) can silently be connected to a stale/wrong database — caused a confusing "relation does not exist" error mid-migration; always double check host/port/database in the active connection tab before running DDL
- `\d tablename` and other psql meta-commands don't work in GUI query editors — use `information_schema.columns` and `pg_constraint` / `pg_get_constraintdef` instead for schema inspection
- Postgres requires a column to be `UNIQUE` or `PRIMARY KEY` before another table can have a `REFERENCES` foreign key pointing at it
